# Lenovo firmware update via XClarity Essentials OneCLI (scan → compare → flash)

**Status:** Findings / design record — sourced from the Lenovo OneCLI User Guide
and on-hardware validation of the Redfish path (ThinkSystem SR650 V3)
**Date:** 2026-09-28

Companion to
[lenovo-redfish-updatefromrepository.md](lenovo-redfish-updatefromrepository.md)
(the Redfish `UpdateFromRepository` path) and
[metal-operator-firmwareupdater-lenovo.md](metal-operator-firmwareupdater-lenovo.md)
(the thin Redfish client). This document describes the **OneCLI** path, which is
the pragmatic alternative when the whole-bundle Redfish path is not viable.

---

## 1. Why OneCLI (the motivation)

On-hardware testing of the Redfish `UpdateFromRepository` path against a real
ThinkSystem SR650 V3 surfaced two blockers that make the **whole-bundle** Redfish
approach unusable for these servers:

1. **XCC storage / size ceiling.** XCC has ~2 GB internal staging space
   (`BundleRepoAvailableSpaceInKB`) and the multipart push path caps at
   `MaxImageSizeBytes: ~250 MB`. The full SR650 V3 System Firmware Bundles
   (~900 MB–1 GB compressed) unpack beyond the staging space; XCC downloads the
   bundle but fails to process it. Lenovo's own Support portal flags these
   bundles: *"Due to the file size this update cannot be processed by XCC
   directly. Please, use LXCE to process this update."* The XCC "Update from
   Repository" UI throws an error when pointed at a full bundle.
2. **Ambiguous no-op / dry-run contract.** The Redfish `GetRepoUpdateDetail`
   dry-run is asynchronous and undocumented: on an already-current server it
   returns `{"ActionState":0,"SyncRepoResult":null}` and stays there, and a
   no-op `UpdateFromRepository` terminates the Redfish Task as a failure with an
   empty message — indistinguishable from a real failure.

**OneCLI** (Lenovo XClarity Essentials OneCLI) is the automatable form of the
"use LXCE" guidance. It is a scriptable command-line tool that operates
**out-of-band against the XCC over the network** (no host-OS agent required),
handles per-component selection, ordering, prerequisites, and (on V3) staging to
XCC2. It sidesteps both blockers: components are applied individually (small
payloads fit the staging space) and the no-op decision falls out of the
`compare` step cleanly.

**References:** Lenovo XClarity Essentials OneCLI User Guide —
<https://pubs.lenovo.com/lxce-onecli/>. Remote-update how-to (HT511327) —
<https://support.lenovo.com/in/en/solutions/ht511327>.

## 2. The three-step workflow

OneCLI models a firmware update as three explicit steps whose XML outputs chain
into each other. Running them explicitly (rather than letting `flash` do its own
scan+compare internally) is what lets the controller **inspect the compare
result and gate on it** before flashing.

| Step | Command | What it does | Output |
| --- | --- | --- | --- |
| 1. Scan | `onecli update scan --bmc <xcc>` | Read **installed** firmware inventory from the server (via XCC) | scan XML (installed versions) |
| 2. Compare | `onecli update compare --dir <bundle> --bmc <xcc> --output <dir>` | Diff **installed vs bundle** versions, check prerequisites, order the updates | **compare XML** (recommended set — empty if nothing to upgrade) |
| 3. Flash | `onecli update flash --comparexml <compare.xml> --dir <bundle> --bmc <xcc>` | Apply **exactly** what the compare XML recommends, in order | flash result XML (+ FFDC on error) |

From the User Guide (`compare`): *"compare the list of installed firmware and
device drivers … to the available update list … and recommend a set of updates
to apply. The XML file generated by the compare command can be used by the flash
command."* It *"checks the prerequisite requirements for all update packages and
lists updates in their required order for the flash command."*

**The no-op gate is step 2's output.** If `compare` finds nothing out of date,
the recommended set is empty → nothing to flash → the controller marks the
`FirmwareUpdate` `Completed` without parking or touching the server. This is the
clean no-op detection the Redfish path could not provide.

## 3. Multi-component orchestration is OneCLI's job, not the controller's

A single `flash` call applies the **whole** recommended set — the controller
does **not** loop per component. From the User Guide:

- `flash` *"deploy[s] updates in sequence, from the list generated by the compare
  command."* Ordering and prerequisites are handled by `compare`/`flash`.
- **ThinkSystem V3 bundle/staging model:** *"OneCLI package[s] all these firmware
  components into a ZIP file and stage[s] this file to XCC2. By default, XCC2 will
  apply these firmware after the system is reset."*
  ```
  onecli update flash --bmc <xcc> --dir <bundle> --bundle --applytime onreset
  ```
- OneCLI also handles inter-component reboots: *"OneCLI restarts the server
  automatically after some components are updated (for example, Hard Drive and
  Broadcom NX1 Network adapters)."*

**Division of labour:**

| Concern | Owner |
| --- | --- |
| Which components need upgrading | OneCLI (`compare`) |
| Sequencing / ordering / prerequisites | OneCLI |
| Applying multiple components (bundle → XCC2 on V3) | OneCLI / XCC2 |
| Inter-component reboots during flash | OneCLI / XCC2 |
| Workflow: park → scan/compare (gate) → flash → poll → boot-from-disk → unpark → status | **Controller** |

## 4. ThinkSystem V3 staged-task model

On V3, `flash --bundle` **stages** the task to XCC2 with an `applytime`
(`Immediate`, `OnReset`, `OnStartUpdateRequest`). The controller then drives the
staged task with:

- `onecli update checktask --bmc <xcc> [--taskid <id>]` — poll status
- `onecli update startstaged --bmc <xcc> [--taskid <id>]` — start a task staged
  with `applytime OnStartUpdateRequest`
- `onecli update canceltask --bmc <xcc> [--taskid <id>]` — abort

This maps onto the existing "issue → poll task → complete" state machine (the
same shape used for the Redfish `UpdateFromRepository` Task, with `checktask` in
place of the Redfish Task poll).

**Reboot control:** with `applytime onreset`, *"XCC2 firmware will not be
restarted automatically … users should manually restart XCC2"* (web UI or
`rebootbmc`). That reset is the point at which the controller's
`ServerMaintenance` / park gating applies — OneCLI controls **what** is flashed,
the controller controls **when** the reset happens.

## 5. Repository / bundle location (`--dir` vs `--fileserver`)

Two ways OneCLI reaches the firmware packages — both work air-gapped (skip
`acquire`, which is the internet-download step):

- **`--dir <folder>`** — a **local** package directory. Mount the extracted
  bundle into the pod and point `--dir` at it. This is the simplest for a
  sidecar.
- **`--fileserver <scheme>://[user:pwd@]host[:port][/path]`** — a **remote** file
  server the XCC pulls from. **For XCC, the supported schemes are `sftp`, `http`,
  `https`** (e.g. `https://user:pwd@10.240.0.1/tmp`). Use this to point at an
  internal HTTPS repo.

**CIFS/SMB is not a supported `--fileserver` scheme for XCC** (only
sftp/http/https). For a CIFS-hosted bundle, mount the share into the pod and use
it as a local `--dir`.

**ThinkSystem OOB needs no external file server:** *"An SFTP server is not
required for OOB (Out-Of-Band) update on ThinkSystem."* So for V3 the sidecar can
run with a local `--dir` and no side-car SFTP/HTTPS server at all.
(`--fileserver`/port 6990 is mandatory only for System x.)

## 6. Connectivity and auth

- **`--bmc userid:password@host[:port]`** puts OneCLI in **out-of-band mode**
  (*"If the --bmc parameter is specified, OneCLI runs in out-of-band mode"*) —
  the sidecar reaches the XCC over the network, no host-OS agent. IPv4 and IPv6
  are supported.
- **IPMI is not a hard prerequisite.** *"When necessary, OneCLI will
  automatically enable CIM-over-HTTPs and IPMI-over-LAN on BMC if disabled, and
  restore them to their original state before exiting."*
- **`--redfish`** forces OneCLI to *"communicate with BMC through Redfish API
  directly"* — for V3 this avoids IPMI-over-LAN/CIM entirely and is the cleaner
  option where IPMI is deliberately disabled for security.
- **Credentials handling:** prefer a credentials file (`--configfile`, template
  `Sample/credentials_config.json`) or `--config` over putting the BMC password
  on the command line (argv is visible in process listings). Populate from the
  `BMCSecret` at runtime.
- **`--forceid <ids>` / `-F` (also on `compare`)** adds a force tag that
  supports **downgrades** (*"Force to downgrade … Ignore the 'never' section …
  Ignore the missing of prereq"*), including `--forceid all`. This is the
  forced-downgrade capability the Redfish `UpdateFromRepository` path lacked, and
  satisfies the "even a lower bundle version must be respected/flashed" policy.

## 7. Controller state machine (OneCLI adapter)

```
Pending
  └─ (no dry-run needed — compare is the gate)
InProgress
  ├─ handleServerMaintenance  → park the Server (reboot safety gate)
  ├─ onecli update scan       → installed inventory        (scan.xml)
  ├─ onecli update compare    → recommended set            (compare.xml)
  │     ├─ empty   → cleanup maintenance → Completed  (no-op; nothing flashed)
  │     └─ nonempty→ record "N components pending" in status, continue
  ├─ onecli update flash --comparexml compare.xml [--bundle --applytime onreset]
  ├─ onecli update checktask  → poll to terminal (V3 staged-in-XCC2)
  ├─ set boot-from-disk (PXE-after-upgrade fix)
  └─ cleanup ServerMaintenance (unpark) → Completed
Failed
  └─ cleanup ServerMaintenance (unpark) — never strand the Server parked
```

The controller parses `compare.xml` for the go/no-op decision and to populate the
`FirmwareUpdate` status with the exact component list; OneCLI owns everything
else (selection, ordering, prerequisites, bundling, apply).

## 8. Deployment shape (sidecar / job pod)

- Bake the **Linux OneCLI** binary (x86_64 or aarch64) into a container image and
  push to the internal registry (air-gapped — no runtime download from Lenovo).
- The controller invokes OneCLI as a **per-update Job pod** (or sidecar): the pod
  reaches the XCC over the cluster network, with the extracted bundle mounted at a
  local path (`--dir`) or an internal HTTPS repo (`--fileserver https://…`).
- **Consistency:** integrate OneCLI the same way HPE **SUM** is wrapped for HPE
  servers (the team's chosen HPE path). One integration pattern for both vendor
  tools; Dell stays pure Redfish (metal-operator PR #1142). All three sit behind
  the single vendor-agnostic `FirmwareUpdate` CRD and one controller state
  machine, dispatched per `Server.Manufacturer`.

## 9. Open items to confirm

- **Licensing / redistribution:** whether OneCLI may be embedded and shipped in an
  air-gapped container image, and the license terms (align with the SUM
  redistribution decision).
- **`--includeid` token vs FirmwareInventory:** `--includeid` takes Lenovo
  **package IDs** (e.g. `lnvgy_fw_imm2_tcoo26k-3.73_anyos_noarch`) from the bundle
  metadata / compare XML — confirm the mapping the controller uses to name
  individual components.
- **`--redfish` for V3 OOB:** confirm OneCLI operates entirely over Redfish with
  no IPMI-over-LAN / CIM dependency, so IPMI can stay disabled on the BMCs.
- **checktask status shape:** the exact task-status structure `checktask` returns
  (states, percent, terminal/failure classification) for the controller poll loop.
